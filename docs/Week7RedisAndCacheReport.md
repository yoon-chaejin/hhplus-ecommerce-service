# 배경
과제 : 조회가 오래 걸리는 쿼리에 대한 캐싱, 혹은 Redis 를 이용한 로직 이관을 통해 성능 개선할 수 있는 로직을 분석하고 이를 합리적인 이유와 함께 정리한 문서 제출

Redis 와 캐시를 도입하기 전에 보다 근본적으로 생각해보면 서비스에 대용량 트래픽이 발생했을 때, 성능이 저하될 수 있는 부분에는 무엇이 있는지에 대해 분석이 필요합니다.
## 조회 시
조회 시점에는 1) 연산이 오래 걸리는 쿼리가 있어서 커넥션을 오래 점유할 때 또는 2) 락에 의해 대기가 발생할 때 DB에서의 작업이 느려질 수 있습니다.
DB에서의 작업이 느려지는 경우, DB커넥션의 점유 시간이 늘어나게 되며, 애플리케이션 단에서 커넥션을 획득하기 위해 대기하는 시간이 발생하게 됩니다.
이를 해결하기 위해서 DB 단 연산 속도를 높이기 위해 인덱싱 및 쿼리 튜닝을 시도하거나, 락의 범위를 줄이거나 락을 사용하지 않도록 로직을 변경할 수 있습니다.
하지만 이런 개선 방안에는 개선할 수 있는 한계가 존재하고, 비즈니스가 복잡해질수록 개선하기 어려운 부분이 발생합니다.

## 변경 시
동시성 제어를 위해 락을 사용함으로 인해 대기하는 요청이 많아지는 경우 성능이 저하될 수 있습니다.

# 문제 제기
이커머스 시나리오에는 다음과 같은 총 7가지의 API가 존재합니다.
- [변경] 포인트 충전
- [조회] 포인트 잔액 조회
- [조회] 상품 목록 조회
- **[조회] 인기 판매 상품 조회**
- **[변경] 선착순 쿠폰 발급**
- [조회] 보유 쿠폰 목록 조회
- **[변경] 상품 주문 및 결제**

각각의 API 요건을 고려해보면 다음과 같이 성능을 개선할 수 있음을 확인할 수 있습니다. 
1. 조회 관련 API 에는 대용량 트래픽과 관련해서 언제나 “캐싱”을 고려해볼 수 있다.<br/>
  이 때, 해당 데이터가 얼마나 자주 변하는지, 데이터의 정합성이 사용자에게 얼마나 중요한지, 얼마나 자주 검색되는지, 데이터를 원본 저장소에서 조회할 때 얼마나 오래 걸리는지 등을 고려해볼 수 있다.
    - [조회] 포인트 잔액 조회 : 변동 (중) / 정합성 (상) / 빈번 (하) / 복잡도 (하)
    - [조회] 상품 목록 조회 : 변동 (중) / 정합성 (중) / 빈번 (상) / 복잡도 (중)
    - **[조회] 인기 판매 상품 조회 : 변동 (-) / 정합성 (하) / 빈번 (상) / 복잡도 (상)**
    - [조회] 보유 쿠폰 목록 조회 : 변동 (중) / 정합성 (상) / 빈번 (하) / 복잡도 (중)

2. 변경 관련 API 와 관련해서는 앞서 동시성 문제에 대한 과제에서 다음과 같이 정의했습니다.<br/>
  ”1명의 사용자(=사람)는 악의를 가진 게 아닌 이상 동시에 작업을 요청할 가능성이 낮다고 가정”한다<br/>
  따라서 쿠폰 사용 및 포인트 충전/차감 로직은 “충돌이 발생할 가능성이 적다.” <br/>
  그렇다면 변경 관련 API 에서 대용량 트래픽에 다른 성능 저하를 고려할 수 있는 건 아래와 같습니다.
    - [변경] 선착순 쿠폰 발급
    - [변경] 상품 주문 및 결제

# 개선 방안
- 이번 주차는 위와 같이 분석한 내용을 기반으로 Redis 를 활용한 성능 개선을 진행할 예정입니다.
  - **[조회] 인기 판매 상품 조회** : 레디스를 캐시로 활용
  - **[변경] 선착순 쿠폰 발급** : 레디스를 이벤트 브로커로 활용

# 고려사항
## 캐시에 대해서
- 데이터의 원본보다 더 빠르고 효율적으로 액세스할 수 있는 임시 데이터 저장소입니다.
- 다음과 같은 경우에 캐시 도입 시 성능 개선을 대할 수 있습니다.
    - 원본 데이터 저장소에서 데이터를 검색하는 시간이 오래 걸리거나 계산이 필요하며, <br/>
    캐시에서 데이터를 가져오는 것이 원본 데이터 저장소 데이터에서 가져오는 것보다 빠릅니다.
    - 이 때, 캐시에 저장된 데이터는 잘 변하지 않는 데이터입니다.
    - 또한, 캐시에 저장된 데이터는 자주 검색되는 데이터입니다.
- 컴퓨터 과학에서 캐시는 CPU와 디스크 사이에 위치하는 임시 저장소입니다.
    - 캐시를 효율적으로 동작하기 위해서 저장할 데이터는 시간적 / 공간적 지역성을 가져야 합니다.<br/>
    지역성이란 데이터에 대한 접근이 시간적으로(가까운 미래에), 공간적으로(가까운 주소에) 가깝게 일어나는 것을 의미합니다.
- 웹 애플리케이션에서는 다음의 위치에서 캐시를 활용할 수 있습니다.
    - 브라우저 캐시
    - 서버 내 메모리 캐시
    - 별도의 캐시 저장소
    - 데이터베이스 캐시
    - CDN 캐시
## 캐시 스탬피드 현상
- 캐시에서 특정 키가 만료되는 시점에 여러 개의 애플리케이션에서 한꺼번에 데이터베이스에 가서 데이터를 “중복 읽기”하고 캐시에 “중복 쓰기”하는 상황
- 통상적으로 캐싱한 데이터는 원본 저장소에서 오래 걸리는 경우가 많아, 위와 같은 상황에서 원본 저장소에 부하가 발생해 서비스 지연 또는 서비스 오류가 발생할 수 있습니다.
- 이에 대한 대응 방안으로는 적절한 만료 시간을 절성하거나 PER 알고리즘을 활용해 만료 전에 데이터를 갱신하는 방안이 있습니다.
  - 적절한 만료 시간 설정 : 캐시 스탬피드를 줄이기 위한 가장 간단한 방법은 만료 시간을 너무 짧지 않게 설정하는 것
  - PER 알고리즘 : Probablistic Early Recomputation (확률적 조기 재계산) 알고리즘으로 데이터를 갱신함<br/>
    currentTime - ( timeToCompute * beta * log(rand()) ) > expiry
