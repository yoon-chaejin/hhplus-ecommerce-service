# 가상 장애 대응 문서

## 1. 장애 개요
- 장애 발생 일시: YYYY-MM-DD HH:MM
- 영향 범위: (예: API 서비스, DB, 특정 사용자 그룹 등) 
- 장애 유형: (예: 서버 다운, 성능 저하, 데이터베이스 연결 오류 등) 
- 발견 경로: (예: 모니터링 시스템 알림, 고객 문의, 내부 테스트 등)

## 2. 초기 대응 절차
- 장애 확인 
- 모니터링 도구 확인 (예: Prometheus, New Relic, Datadog)
- 로그 분석 (예: Kibana, CloudWatch, Splunk)
- 네트워크 상태 확인 (예: Ping, Traceroute, Netstat)
- 대응 팀 구성 및 역할 지정 
  - Incident Manager: 장애 대응 총괄 
  - Infrastructure Engineer: 서버 및 네트워크 점검 
  - Database Engineer: 데이터베이스 관련 문제 해결 
  - Application Engineer: 애플리케이션 코드 및 API 점검 
  - Communication Manager: 내부 및 외부 커뮤니케이션 담당
- 장애 전파 및 공유 
- 내부 공지 (Slack, Teams 등)
- 고객 공지 (상황에 따라 이메일, 상태 페이지 업데이트)

## 3. 원인 분석 
- 초기 원인 분석 (Immediate Cause Analysis)
- 최근 배포 내역 확인 (CI/CD 로그)
- 장애 발생 직전 변경 사항 확인 (코드, 설정, 네트워크 등)
- 관련 서비스 및 종속성 확인 
- 근본 원인 분석 (Root Cause Analysis - RCA)
- 장애 발생 패턴 분석 
- 로그 및 메트릭 비교 
- 동일 유형의 과거 장애 사례 검토

## 4. 해결 조치 
- 임시 조치 (Hotfix): 서비스 복구를 위한 빠른 해결책 적용 
- 영구적 해결책 (Long-term Fix): 재발 방지를 위한 근본적인 개선책 마련

## 5. 사후 대응 및 개선 
- 포스트모템 작성 
- 장애 개요 및 영향 분석 
- 원인 및 해결 과정 문서화 
- 향후 예방 조치 제안 
- 재발 방지 대책 
- 모니터링 및 경고 시스템 개선 
- 장애 대응 프로세스 개선 
- 코드 리뷰 및 테스트 강화 
- 팀 내 공유 및 교육 
- 장애 대응 프로세스 개선 내용 공유 
- 유사 장애 발생 시 대응 훈련 실시

## 6. 참고 자료 
- 로그 경로 및 분석 결과 
- 관련 문서 및 내부 위키 링크 
- 장애 발생 시점의 시스템 스냅샷 (가능한 경우)
